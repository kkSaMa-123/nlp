# 一种带更新与反思机制的轻量级长期记忆对话智能体

**作者**：计鑫楷、张嘉杰、张闻曦 · 南京大学

---

## 摘要

长期对话记忆对于对话智能体在多次会话中保持连贯交互至关重要。现有方法存在明显不足：无记忆智能体遗忘所有历史上下文；全上下文智能体产生难以承受的 token 开销与延迟；原始轮次检索增强生成（RAG）则引入非结构化对话带来的噪声。本文提出一种轻量级记忆智能体，从原始对话中提取结构化记忆，通过更新机制进行去重与合并，并在活跃记忆之上生成高层反思。在涵盖四个类别（时间推理、开放域、单跳、多跳）的 40 题基准评测上，我们的"更新+反思"智能体取得了 0.325 的 Judge Score，高于原始轮次 RAG 的 0.263，同时回答速度比全上下文快 6 倍（1.22s vs. 7.31s）。消融实验证实细节笔记与记忆更新是最有效的组件，而反思在事实型问题上收益有限。失败分析揭示多跳推理是主要瓶颈，为未来改进指明了方向。

---

## 1. 引言

随着对话式 AI 系统部署周期越来越长——跨越数天、数周甚至数月的用户交互——记住并利用历史对话的能力变得至关重要。一个在每次会话后便遗忘用户偏好、生活事件或已分享上下文的对话智能体，无法提供个性化或连贯的体验。这一*长期对话记忆*问题日益受到学术界和工业界的关注。

当前赋予智能体记忆的方法可归纳为三种范式。**无记忆智能体**独立处理每个查询，丢弃所有历史上下文——它们成本低、速度快，但根本上无法利用过往交互。**全上下文智能体**将完整对话历史拼接进提示词；虽然保留了全部信息，但注意力机制的平方级复杂度使该方案随着对话增长变得极其昂贵且缓慢。**原始轮次 RAG** 从向量库中检索相关对话轮次，缩短了上下文长度，但检索到的轮次充满噪声、结构松散，缺乏高效推理所需的抽象。

本文提出一种结构化记忆流水线以应对上述局限。我们的智能体不直接存储原始对话轮次，而是首先用轻量级大语言模型从会话中**提取**结构化事实与细节笔记。这些记忆随后经过**更新器**，将新记忆与已有记忆进行比较，执行去重、合并或替换操作。**反思**模块定期从活跃记忆群中合成高层抽象——例如，从累积的事实观察中推断用户的性格特征或长期偏好。

我们的核心见解是：这一*提取–更新–反思*流水线以一次性的摄入成本（每个会话的记忆提取）换取了回答时大幅降低的推理成本——只需检索一小部分相关的、结构化的记忆并将其纳入提示词。我们在涵盖四个类别的 40 题基准上，以 Qwen2.5-3B 为生成模型、DeepSeek-V4-Pro 为 LLM 评判者，将本系统与三个基线进行了对比评估。

本文的贡献有三点：

1. **一种新的记忆智能体框架**，将事实提取、细节笔记保留、基于规则的记忆更新与高层反思整合为统一的轻量级流水线。
2. **系统的消融实验与失败分析**，量化了各组件（细节笔记、更新、反思）的贡献，并识别出多跳推理为主要失败模式。
3. **一套可复现的开源基准**，所有代码、提示词与评测数据均公开可获取。

## 2. 相关工作

### 2.1 对话记忆与检索增强生成

跨对话轮次维护状态的问题已被广泛研究。早期工作聚焦于填槽式对话状态追踪；近年来，检索增强生成（RAG；Lewis 等，2020）已成为了为 LLM 提供外部知识的主流范式。LangChain 和 LlamaIndex 等系统提供了存储和检索对话历史的记忆模块，但通常是基于原始对话轮次而非结构化的抽象记忆进行操作。

Mem0 是与之密切相关的方法，从对话中提取结构化记忆并执行去重与冲突消解。本文建立在类似原则之上，但聚焦于长期、多会话场景，并强调轻量级、可本地部署的模型。

### 2.2 长期智能体记忆

AI 智能体中的长期记忆概念因 *Generative Agents* 框架（Park 等，2023）而广受关注，该框架引入了记忆流架构，包含三个关键操作：记忆检索（按新近度、重要性和相关性）、记忆反思（合成高层推断）和记忆规划。我们的反思模块直接受此工作启发，适配于更简洁的、基于检索的流水线。

MemoryBank（Zhong 等，2023）引入了受艾宾浩斯遗忘曲线启发的记忆保持机制，对记忆随时间衰减进行建模。虽然我们未实现遗忘机制，但该方向是本框架的自然扩展。

其他值得关注的方法包括 MemGPT（Packer 等，2023），将记忆视为虚拟上下文管理问题；以及 ChatDev（Qian 等，2023），使用具有共享记忆的交流智能体进行软件开发。

### 2.3 记忆更新与反思

记忆更新——当新信息到达时决定添加、合并或替换已有记忆——对防止记忆膨胀和矛盾至关重要。基于规则的方法使用文本相似度阈值进行判断，而基于 LLM 的方法则提示模型推理语义等价性。本系统采用基于规则的更新以追求效率，同时提供基于 LLM 的选项以获取更高精度。

反思，如 Generative Agents 中所引入，是指提示 LLM 在给定一组相关观察后生成抽象的高层陈述。我们将此技术应用于活跃记忆群，生成可能在单条记忆中并未明确陈述的个性摘要、偏好模式及关系推断。

### 2.4 LLM-as-Judge

使用强语言模型评估弱模型的输出质量已成为标准的评测协议（Zheng 等，2023）。我们采用此范式，使用 DeepSeek-V4-Pro 作为云端评判者对模型预测在 0–1 正确性尺度上进行评分，提供了比纯精确匹配指标更细粒度的评估。

### 2.5 本文定位

本文在设计空间中占据特定位置：一种**低成本、动态维护的记忆智能体**，面向可本地部署的模型（3B 参数量），并强调结构化记忆抽象优先于原始轮次检索。这使其介于重量级云端记忆系统与纯检索基线之间。

## 3. 方法

### 3.1 整体架构

图 1 展示了本记忆智能体的完整流水线。系统在两种阶段中运行：**摄入阶段**将会话处理为结构化记忆，**查询阶段**检索相关记忆以回答问题。

│       ▼                                                       │
│  ┌─────────┐    ┌──────────┐    ┌────────────┐              │
│  │ Writer  │───▶│ Updater  │───▶│ Reflection │              │
│  │(提取    │    │(去重/    │    │(高层总结)  │              │
│  │ 事实 +  │    │ 合并/    │    │            │              │
│  │ 细节)   │    │ 更新)    │    │            │              │
│  └─────────┘    └──────────┘    └────────────┘              │
│                                       │                       │
│                                       ▼                       │
│                                 ┌──────────┐                 │
│                                 │  向量库  │                 │
│                                 └──────────┘                 │
│                                                              │
├─────────────────────────────────────────────────────────────┤
│                      查询阶段                                │
│                                                              │

│       │                                                       │
│       ▼                                                       │
│  ┌───────────┐    ┌────────────┐    ┌──────────┐           │
│  │ Retriever │───▶│ Controller │───▶│  回答    │           │
│  │ (top-k    │    │ (提示词 +  │    │          │           │
│  │  余弦)    │    │  上下文)   │    │          │           │

**图 1**：系统架构。摄入阶段，每个对话会话依次经过 Writer（提取事实与细节笔记）、Updater（去重与合并）和 Reflection（高层合成）。生成的活跃记忆存入向量数据库。查询阶段，Retriever 找到 top-*k* 最相似记忆，Controller 将其与问题组合后生成回答。

### 3.2 Writer：记忆提取

Writer 模块负责将原始多轮对话转换为结构化记忆。给定一个对话会话（由两个说话者之间带有时间戳的消息序列组成），Writer 提示语言模型提取两类记忆：

- **事实**（`type=fact`）：对对话中讨论的实体、事件、关系、偏好等信息的简洁、自包含陈述。每条事实带有时间戳并归属于相应的说话者。
- **细节笔记**（`type=detail`）：在摘要中易丢失的具体、细粒度信息——日期、书名、食物名称、车辆型号、数值、地点名称等。这些信息单独存储，因为它们在回答细节型问题时至关重要，但模型做高层总结时往往会被忽略。

提取提示词指示模型每个会话生成固定数量的事实记忆（默认 $m=4$），并在启用 `MEMORY_DETAIL_NOTES` 标志时附带细节笔记。每条记忆以 JSON 对象存储，包含 `type`、`content`、`timestamp` 和 `speaker` 字段。

### 3.3 Updater：记忆管理

随着新会话不断摄入，Updater 将每条新提取的记忆与已有记忆库进行比较，以防止重复并管理矛盾。对于每条新记忆，系统按余弦相似度检索最接近的已有记忆，并执行以下四种操作之一：

- **ADD**：新记忆与所有已有记忆足够不同，作为新的活跃记忆插入。
- **IGNORE**：新记忆与已有记忆语义等价（余弦相似度高于合并阈值），予以丢弃。
- **MERGE**：新记忆与已有记忆相似但不相同；已有记忆的内容将融入新信息。
- **UPDATE**：新记忆与已有记忆矛盾；旧记忆标记为废弃并被替换。（此操作仅在启用基于 LLM 的更新时可用。）

在默认配置中，我们使用基于规则的更新器（`MEMORY_UPDATE_USE_LLM=0`），依赖余弦相似度阈值。在小样本实验中，5 个对话会话的统计结果如下：854 条提取记忆 → 677 条活跃记忆（177 条重复被合并或忽略）。最频繁的操作是 MERGE（169 次），表明对话中包含大量重叠或渐进式精炼的陈述，而非直接矛盾。

### 3.4 Reflection：高层记忆合成

受 Generative Agents（Park 等，2023）中反思机制的启发，我们的 Reflection 模块定期从累积的活跃记忆中合成高层抽象。给定一组活跃记忆（按新近度排序，具有可配置的数量上限），模块提示 LLM 生成少量反思性陈述——例如，推断性格特征、关系动态或长期行为模式。

在我们的实验中，5 个对话会话生成了 16 条反思记忆（配置 `MEMORY_REFLECTIONS=6`）。这些反思与普通事实和细节记忆一起存储在向量库中，在查询时以相同方式检索和使用。

### 3.5 Retriever 与 Controller

**Retriever**：查询时，使用与摄入阶段相同的嵌入模型（all-MiniLM-L6-v2）对用户问题进行嵌入。按余弦相似度检索 top-$k$ 条最相似记忆（默认 $k=10$）。

**Controller**：Controller 构建一个提示词，包括：（1）用户当前问题，（2）检索到的记忆（按类型、时间戳、说话者和内容格式化），（3）要求简洁回答、若记忆中无足够信息则回复"unknown"的指令。提示词随后发送给生成模型，响应作为智能体的答案返回。

### 3.6 基线系统

我们将本系统与三个基线进行对比：

- **No-Memory（无记忆）**：智能体仅接收当前问题，无法访问任何对话历史。这代表性能下界，检验问题能否仅靠模型参数化知识回答。
- **Full-Context（全上下文）**：所有对话会话（10 段对话共 272 轮）拼接后纳入提示词。这代表可用信息的上界，代价是最高延迟和 token 用量。
- **Raw-Turn RAG（原始轮次 RAG）**：单独对话轮次嵌入后存入向量库。查询时检索 top-$k$ 最相似轮次并纳入提示词。这代表未进行结构化记忆提取的朴素 RAG 基线。

## 4. 实验

### 4.1 实验设置

**数据集**：我们使用 *p10* 评测集，由 `prepare_eval_set.py --per_category 10 --seed 42` 生成。该集合包含 10 段对话，共 272 个对话会话，从中抽取 40 道问题。问题均匀分布在四个类别：

| 类别 | 描述 | 数量 |
|------|------|:----:|
| `temporal`（时间推理） | 时间相关推理（如"X 何时发生？"） | 10 |
| `open_domain`（开放域） | 关于人物的广泛知识问题 | 10 |
| `single_hop`（单跳） | 单个事实即可回答的问题 | 10 |
| `multi_hop`（多跳） | 需要组合 ≥2 个事实的问题 | 10 |

**模型**：所有系统使用 **Qwen2.5-3B-Instruct**（通过 Ollama 本地运行）作为生成模型，同时用于记忆提取和回答生成。嵌入使用 `all-MiniLM-L6-v2` 计算。评测使用 **DeepSeek-V4-Pro**（通过硅基流动云端 API 访问）作为 LLM 评判者。

**指标**：
- **Judge Score**：LLM 评判者给出的 0–1 连续评分，0 = 完全错误，0.5 = 部分正确，1 = 完全正确。
- **F1**：预测答案与参考答案之间的 token 级 F1。
- **EM**：精确匹配准确率。
- **平均延迟**：每个问题的墙上时钟时间，包含检索和生成。

**超参数**：记忆提取每个会话 $m=4$ 条事实，细节笔记已启用。检索使用 $k=10$，纯余弦相似度。更新器使用基于规则的合并，余弦相似度阈值 0.85。反思每个对话生成最多 6 条高层陈述。

### 4.2 主结果

表 1 展示了四个系统在 p10 基准上的总体对比。

**表 1：p10 基准主结果（40 题）**

| 系统 | Judge Score ↑ | F1 ↑ | EM ↑ | 延迟 (s) ↓ |
|------|:-----------:|:------:|:----:|:----------:|
| No-Memory | 0.000 | 0.000 | 0.00 | **0.11** |
| Full-Context | **0.400** | **0.154** | **0.05** | 7.31 |
| Raw-Turn RAG | 0.263 | 0.073 | 0.00 | 0.79 |
| **Update+Reflection（本文）** | **0.325** | **0.119** | 0.00 | **1.22** |

我们的 Update+Reflection 系统取得了 0.325 的 Judge Score，比 Raw-Turn RAG 高出 23.6%（0.263 → 0.325），大幅缩小了与 Full-Context（0.400）的差距。效率方面，本系统平均回答时间为 1.22 秒——比 Full-Context（7.31s）**快 6 倍**——同时回答质量远高于 No-Memory 基线。

延迟优势是结构性的：Full-Context 每个问题都需处理全部 272 轮对话，而我们的系统仅支付一次性摄入成本（会话边界的记忆提取），然后每个查询仅检索 10 条精简的记忆条目。摄入成本在关于同一对话的多次提问中被均摊。

### 4.3 各类别表现

表 2 按问题类别细分 Judge Score。

**表 2：各类别 Judge Score**

| 系统 | 时间推理 | 开放域 | 单跳 | 多跳 |
|------|:--------:|:------:|:----:|:----:|
| No-Memory | 0.000 | 0.000 | 0.000 | 0.000 |
| Full-Context | 0.200 | **0.800** | 0.300 | **0.300** |
| Raw-Turn RAG | 0.250 | 0.600 | 0.200 | 0.000 |
| **Update+Reflection** | **0.500** | 0.500 | 0.200 | 0.100 |

本系统在时间推理问题上表现最佳（0.500），结构化记忆的时间戳可能在此类问题上相比原始轮次检索具有优势。在开放域问题上，Full-Context 占据主导（0.800），表明某些广泛知识问题受益于压缩记忆无法完整捕捉的完整对话上下文。

最显著的模式是所有系统在**多跳问题**上的困难：即便 Full-Context 也仅取得 0.300，Raw-Turn RAG 为 0.000，本系统为 0.100。这揭示了多跳推理是检索式记忆系统的根本瓶颈——单条记忆或许能被正确检索，但智能体无法将其组合以推断答案。

### 4.4 消融实验

为量化各组件的贡献，我们在一个较小的 8 题评测集上用相同的 Qwen2.5-3B 模型进行了消融实验。表 3 报告 token 级 F1 分数。

**表 3：小样本评测集消融结果（8 题）**

| 配置 | F1 |
|------|:----:|
| 纯追加 (m=4, k=6) | 0.231 |
| + 细节笔记 | **0.304** |
| + 更新（基于规则） | 0.289 |
| + 反思 | 0.289 |
| + 谨慎推断提示词 | 0.275 |
| 纯追加 (m=8, k=10) | 0.101 |

消融实验的关键发现：

1. **细节笔记带来了最大的单项提升**（F1 +0.073）。保留摘要中易丢失的具体细节（日期、名称、数字）显著提升了事实型问题的检索质量。

2. **基于规则的更新略微降低了 F1**（0.304 → 0.289），同时将记忆数量从 854 降至 677（减少 20.7%）。这种权衡——以略微降低质量换取更精简的记忆库——在存储受限的部署场景中是可接受的。

3. **反思在此评测集上未展现可测量的提升**（0.289 → 0.289）。小样本问题主要依赖具体事实而非高层人格推断。我们预期反思在包含性格特征和关系动态问题的更大数据集上将更具价值。

4. **更多记忆反而有害**：将每会话 $m=4$ 条事实增至 $m=8$ 使 F1 从 0.231 降至 0.101。这证实检索噪声——检索到不相关或低质量记忆——可能抵消更多候选记忆带来的益处。

5. **谨慎推断**（允许模型使用强间接证据做出"likely/probably"回答）将 unknown 数量从 4 降至 3，但 F1 也从 0.289 降至 0.275，体现了覆盖度与精确度的权衡。

### 4.5 效率分析

表 4 对比了各系统的计算开销。

**表 4：计算开销对比（p10，40 题）**

| 系统 | 总 LLM 调用 | 每问调用 | 回答延迟 (s) |
|------|:---------:|:------:|:----------:|
| No-Memory | 40 | 1.0 | 0.11 |
| Full-Context | 40 | 1.0 | 7.31 |
| Raw-Turn RAG | 40 | 1.0 | 0.79 |
| **Update+Reflection** | 322 | 8.05 | 1.22 |

虽然本系统的总 LLM 调用次数更多（322 vs. 基线的 40），但其中绝大部分（272 次）发生在一次性摄入阶段。查询时仅需一次 LLM 调用（回答生成），外加嵌入检索开销。每问题回答延迟（1.22s）仅略高于 Raw-Turn RAG（0.79s），大幅低于 Full-Context（7.31s）。

摄入成本明细：272 次用于记忆提取（每会话一次，产出 $m=4$ 事实 + 细节笔记），10 次用于反思（每对话一次），40 次用于回答生成。在生产环境中，一个对话摄入一次但被多次查询时，每问题的均摊成本趋近于 1 次 LLM 调用。

### 4.6 失败案例分析

为理解本系统的局限性，我们分析了 Judge Score 为 0（完全错误）的案例。以下展示三种代表性失败模式。各案例的完整检索记忆见附录 D。

---

**案例 1：多跳推理失败（conv-26, q27）**

- **问题**：Caroline 会以写作为职业方向吗？
- **参考答案**：Likely no; though she likes reading, she wants to be a counselor.
- **模型回答**：unknown
- **检索到的 top memories**：所有检索到的记忆均涉及 Caroline 对心理咨询/心理健康工作的兴趣、她的艺术背景和钢琴学习。无一提及写作。
- **诊断**：此问题需要将 Caroline 明确的职业偏好（咨询）与缺乏写作相关证据联系起来——这是一项典型的多跳推理。系统检索到了正确记忆（咨询兴趣），但生成模型（Qwen2.5-3B）未能执行反事实推理以得出她*不会*从事写作的结论，默认输出"unknown"。

---

**案例 2：桥接事实缺失（conv-42, q60）**

- **问题**：Nate 拥有什么游戏主机？
- **参考答案**：A Nintendo Switch; since the game "Xenoblade 2" is made for this console.
- **模型回答**：unknown
- **检索到的 top memories**：检索到的记忆显示 Nate 参加游戏比赛、偏好制作游戏 YouTube 内容、分享手持手柄的照片——但无一明确提及主机品牌或"Xenoblade 2"。
- **诊断**：桥接事实（Nate 玩"Xenoblade 2"→ 因此拥有 Nintendo Switch）要么在写入阶段未被提取，要么在 top-10 检索截断中被排除。这凸显了检索召回问题：必要事实存在于对话中，但未出现在 top-$k$ 结果中。

---

**案例 3：保守回答 unknown（conv-26, q30）**

- **问题**：Melanie 会被视为 LGBTQ 社区成员吗？
- **参考答案**：Likely no, she does not refer to herself as part of it.
- **模型回答**：unknown
- **检索到的 top memories**：检索到的记忆包含大量关于 Caroline 的 LGBTQ 活动信息（她参加了导师项目、活动团体、骄傲游行）——但全部指向 *Caroline*，而非 Melanie。
- **诊断**：系统检索到高度相关但*实体错误*的记忆。嵌入模型将话题（LGBTQ）与人物（Caroline vs. Melanie）混为一谈。这种实体混淆是基于嵌入检索的已知缺陷，提示需要实体感知过滤或基于元数据的重排序。

---

**失败模式总结**：

| 模式 | 频率 | 根因 |
|------|:----:|------|
| 多跳推理失败 | 高 | 生成模型无法组合检索到的事实 |
| 桥接事实缺失 | 中 | 检索召回缺口；事实未进入 top-$k$ |
| 实体混淆 | 中 | 嵌入相似度将不同实体混为一谈 |
| 保守回答 unknown | 中 | 模型不确定时默认输出"unknown" |
| 记忆压缩丢失 | 低 | 提取过程中丢失重要信息 |

最主要失败模式——多跳推理——影响包括 Full-Context 在内的所有检索式系统（Full-Context 在多跳问题上也仅获 0.300）。这表明瓶颈不在于记忆架构本身，而在于 3B 参数生成模型的推理能力。

---

## 5. 讨论

### 5.1 为什么 Full-Context 依然最优？

尽管本系统较 Raw-Turn RAG 有明显提升，Full-Context 仍保持明显领先（Judge Score 0.400 vs. 0.325）。这一差距反映了**信息完整度**与**计算效率**之间的根本权衡。Full-Context 保留了每段对话的全部细节——语气、隐含关系以及记忆提取中不可避免丢失的微妙上下文。我们的结构化记忆本质上是有损的：它捕捉"要旨"而非对话的完整丰富性。

然而，本系统的效率优势是显著的（快 6 倍），且随对话长度线性增长。对于响应速度比对完美精度更重要的应用——个人助手、客服聊天机器人、实时游戏 NPC——我们的方案提供了务实的中庸之道。

### 5.2 本方案适用场景

本系统在以下场景最具优势：
- **延迟敏感**：1.22s vs. Full-Context 7.31s。
- **存储受限**：结构化记忆更紧凑且经过去重。
- **隐私关切**：提取的记忆抽象掉了原始对话文本。
- **每对话多次查询**：一次性摄入成本被均摊。

以下场景则不太适用：
- **需要完美召回**：Full-Context 仍然是金标准。
- **多跳推理为主**：本方案未解决这一根本挑战。
- **语气与潜台词重要**：记忆提取会抹平对话中的微妙线索。

### 5.3 多跳推理挑战

多跳推理是本系统及检索式记忆方法最明显的局限性。所有系统——包括 Full-Context——在多跳问题上表现不佳（最高 Judge Score 0.300）。我们认为这需要的不仅是更好的检索，而是根本不同的架构：

- **多步检索**：基于前一次检索结果迭代检索新记忆。
- **图结构记忆**：以实体和关系而非扁平文本块表示记忆，支持基于路径的推理。
- **更强的生成模型**：本实验中使用的 3B 模型可能根本缺乏复杂多跳推理能力；扩展到更大模型可能带来显著增益。

### 5.4 局限性

除多跳推理外，本文工作还存在若干局限：
- **数据集规模**：p10 基准（40 题）足以进行消融研究，但需要更大规模验证。
- **模型规模**：结果基于 3B 参数模型；更大模型上的性能尚待测试。
- **反思利用不足**：实验未展现反思的明确收益，可能是因为数据集以事实型问题为主。不同问题分布可能揭示其价值。
- **无主动遗忘**：不同于 MemoryBank，本系统没有衰减或遗忘过时记忆的机制。

---

## 6. 结论

本文提出了一种轻量级长期记忆智能体，从对话中提取结构化事实与细节笔记，应用基于规则的更新来管理记忆规模，并生成高层反思。在 40 题基准评测上，我们的 Update+Reflection 系统取得了 0.325 的 Judge Score——较原始轮次 RAG（0.263）提升 23.6%——同时回答速度比 Full-Context 快 6 倍（1.22s vs. 7.31s）。

消融实验证实细节笔记和记忆更新是最有效的组件，反思的收益则取决于上下文。失败分析将多跳推理识别为主要瓶颈，指向多步检索或图结构记忆的需求。

我们的代码与数据均已公开：<https://github.com/kkSaMa-123/nlp>。希望本文能为对话智能体高效、结构化长期记忆的未来研究提供有用的基线。
